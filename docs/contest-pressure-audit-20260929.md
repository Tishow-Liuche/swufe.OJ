## 已确认的缺陷及待证假设

### 优先修复：新页面会话恢复限流

`auth.controller.ts` 对 refresh 限制每用户每分钟 5 次；比赛题目使用新标签打开，每页均恢复会话。真实 API 同账号连续六次串行恢复返回 **200、200、200、200、200、429**；已有访问令牌仍可读取资料。这是新页恢复被拦，不是证明服务端 Cookie 已失效。

前端暂时错误返回未知状态，并不主动清除凭据，但新页面可能无法进入受保护页面。另有代码确认的每 IP 每分钟 300 次认证入口上限：100 人共用出口同时多开页面仍有聚合限流风险，本轮未把该聚合边界作为独立 HTTP 用例复现。

建议保留抗滥用保护，区分有效会话正常续期与无效凭据请求；有效用户/共享出口的额度按赛事多页需求设置并测试，客户端对 429 显示可恢复状态并按 Retry-After 重试。不能简单取消全部限流。

### 优先修复：迟到 401 使用新账号重放旧请求

真实前端客户端配合可控 Axios 适配器复现：A 账号 POST 提交尚未完成时切为 B，A 的迟到 401 到达后，原 POST 和原源码被附上 B 的 Authorization 重放。`api/client.ts` 将“不同访问令牌”一概解释为正常续期，没有区分请求发出后的账号身份切换。

此为离线精确时序复现，不是生产账号被串用的历史证据。仅清内存但 Cookie 仍有效时旧请求会恢复登录；对照用例中，完成服务端退出并撤销 Cookie 后不会复活账号。

建议请求发出时绑定稳定的登录会话代次，账号切换/退出后禁止旧业务请求重放，普通续期不改变该身份代次；尤其不能重放交题等写请求。

### 源码确认：比赛状态边界失败后不自动重试

`ContestArena.vue` 的 load 先清除状态切换定时器，只在请求成功时重建。比赛开始/结束时该请求若发生 429/502，状态可停留在旧值，需要手动重试或导航。本轮为源码确认，未执行真实浏览器故障复现。

建议对临时错误增加有上限退避重试，保留有效页面和登录态，确保销毁/导航取消旧计时器。

### 尚未独立复现：登录与其他 Cookie 写入竞态

登录请求未使用刷新/退出相同的跨页锁，迟到 Set-Cookie 可能覆盖新登录 Cookie。JavaScript 状态代次本身不能撤销浏览器已接受的响应 Cookie。需要真实浏览器或精确 HTTP Cookie 时序测试后再确定修复，不作为已经证实的历史退登原因。

## 容量与后续验收

当前生产配置：每人 5 秒提交间隔，最多 5 个未完成提交，全局等待队列上限 500，判题 8 并行。因此 100 人持续以最大速率提交约 20 份/秒，需要平均每份占用一个判题槽不超过 0.4 秒才可能长期不积压。重题、慢程序或大量输出必然可能排队，不能以网络良好为由保证任何负载均无等待。

下一步应先修复并回归上述确认缺陷，再重跑完整 17 分钟（最好覆盖多个续期周期）、共享出口多标签、最后一分钟、真实判题和公网端到端测试。若仍有连接重置，须记录 reusedSocket、连接生命周期和服务端关联信息定位，不能通过静默重试 POST 掩盖或重复交题。
