# 100 人比赛容量优化与验证（2026-09-28）

## 原因与改动

原压测在 50 人阶段出现 Prisma P2028 事务等待超时；API CPU 约 170%，内存约 148/512 MiB，未发生 OOM 或容器重启。因此优先减少竞争查询，不迁移数据库、不扩大连接池、不调整老师服务器。

- 排名先查最小权限信息，再使用 2 秒短缓存；并发相同请求只执行一次重查询。
- 公共提交列表使用 1 秒短缓存，不再从数据库取无用源码；个人/搜索列表不共用缓存。
- 缓存最多保留 128 个键，满且全部加载中时新键绕过缓存，并非全局并发限制；错误不缓存。
- 缓存隔离管理员和选手、比赛更新版本及未开始/进行/封榜/结束阶段；每次请求重新检查私有赛资格。
- 已签名且未过期的 access token 按账号限流，不让校园网多人共用匿名 IP 配额。
- 登录按实际生效的规范化账号标识 5 次/分钟，另有独立 IP 300 次/分钟上限。用户名和邮箱是不同标识桶。
- 续期在 IP 总限额检查后，查验随机 cookie 的 SHA256 对应未过期会话，按可信 userId 5 次/分钟；撤销不缓存。无效 cookie 仍按 IP 限流。
- 注册、找回密码限制保持原状；注册仍为 5/IP/分钟，赛前应提前注册或导入账号。

## 同机隔离压测

主机为 2 CPU、约 2 GB 内存；测试 API 容器限额 512 MiB，数据库仍共用主机 PostgreSQL、独立 schema，连接池仍为 5。Redis、账号、比赛、提交记录均隔离；生产比赛和老师判题机未承受测试提交。

初始 fixture 为 100 人、8 题、2000 条历史提交。每人每 5 秒提交，同时每 5 秒分别请求排名和提交列表、每 30 秒请求题面，比真实界面的单页 10 秒轮询更密集。12 秒客户端超时；错误和主机健康阈值自动中止。请求经 SSH 隧道访问测试 API；不是实际浏览器完整渲染测试。

| 场景 | 优化前 | 优化后首轮 |
| --- | --- | --- |
| 50 人排名 P95 | 5834 ms | 159 ms |
| 50 人提交列表 P95 | 9166 ms | 69 ms |
| 50 人提交请求 | 60 成功、5 冷却拒绝、14 HTTP 500、41 超时 | 185 成功、115 冷却拒绝、无 500/超时 |
| 100 人混合负载 90 秒 | 50 人阶段已安全停止 | 1076 成功提交、724 冷却拒绝；排名 P95 256 ms，列表 106 ms，无 500/超时 |
| 同 IP 100 人混合负载 30 秒 | 另测 120 次题面访问有 20 次 429 | 377 成功提交、223 冷却拒绝，所有读请求成功，无 500/超时 |

初版优化以每人 5.2 秒提交运行 120 秒：2308 次请求，2266 次接受、42 次 5 秒冷却拒绝；成功提交 P95 239 ms，排名 488 ms，列表 160 ms。不能把 429 当成成功吞吐。精确贴近 5 秒边界时，网络和处理时间波动会导致冷却拒绝。

最终认证改动的真实集成测试：同一 IP 100 个账号同时登录全部 HTTP 200（P95 8717 ms）；100 个真实会话续期全部 200（P95 517 ms）；轮换后再次续期全部 200（P95 457 ms）。并发登录的密码哈希开销明显，建议赛前登录。

最终构建再次执行同 IP 100 人、每人 5.2 秒提交、120.203 秒混合负载：2308 次提交请求，2248 次接受、60 次冷却拒绝，实际接受约 18.7 次/秒；成功提交 P95 327 ms，排名 2400/2400 成功、P95 697 ms，列表 2400/2400 成功、P95 219 ms，题面 400/400 成功。无 HTTP 500、超时或安全中止。此轮沿用前几轮累积的隔离测试记录，不是重建 2000 条 fixture；最终版在较大历史集上复验。中途一次 SSH 隧道断开导致启动探针超时，未开始施压；重建隧道后以上完整运行通过，不将该探针归为 API 负载失败。

公开 HTTPS 首页 HTML 与入口 JS 同时 100 人各请求一次，200/200 成功；这不包含全部静态资源、浏览器渲染和用户网络差异。

## 自动化验证与边界

最终后端全量 65 suites / 597 tests 通过，`npm run build` 通过，独立安全与质量审查通过。回归涵盖私有赛缓存命中前权限、管理员/封榜/结束隔离、仅时间推进的边界切换、个人筛选、失效 JWT、同 IP 多账号、会话撤销及实际 LoginDto 的字段选择。

压测的判题消费为隔离模拟消费并写入测试结果，不执行真实用户代码。以上证明当前 API/数据库在该短时负载下的表现，不能推出任意题目判题速度、500 人容量、长时间稳定或零故障保证。判题并发 8、用户提交冷却 5 秒、个人待评测上限 5、全局队列上限 500 均未调整；真实队列等待取决于测试数据与程序耗时。
